## 1. ใช้เอกสารนี้อย่างไร

เอกสารนี้อธิบายเกมทั้ง 7 เกม วิธีเล่นบนมือถือ หน้าที่ผู้จัด คะแนน และจังหวะเชื่อมกับสไลด์ปัจจุบัน เพื่อให้พัฒนาระบบกิจกรรมแยกแล้วนำกลับมาตรวจร่วมกันได้

**สถานะปัจจุบัน:** เว็บสไลด์มีหน้าชื่อเกม บทผู้พูด และคิวการนำเสนอแล้ว แต่ยังไม่มีระบบเข้าห้อง เล่นเกม รับคำตอบ หรือคิดคะแนน เอกสารนี้เป็นแบบสำหรับระบบที่จะทำเพิ่ม ไม่ใช่รายงานว่าฟังก์ชันเหล่านี้ทำเสร็จแล้ว

**กติกาและคะแนนด้านล่างเป็นข้อเสนอฉบับพร้อมพัฒนารอบแรก** ปรับจากแนวคิดต้นฉบับให้เล่นจริงในเวลาที่มี โดยเฉพาะเกมภาพที่เพิ่มใหม่ การโหวตแคปชั่น และเกมตัดสินใจ หากเลือกเปลี่ยนกติกา ให้แก้เอกสารนี้พร้อมระบบ เพื่อใช้เป็นเกณฑ์ตรวจงานครั้งต่อไป

## 2. รูปแบบกิจกรรมรวม

ผู้ฟังเล่นผ่านเว็บบนมือถือแนวตั้ง ไม่ต้องติดตั้งแอป สแกน QR ครั้งเดียว กรอกชื่อเล่น เลือกหนึ่งใน 8 กลุ่ม แล้วอยู่ในห้องเดิมตลอดงาน เมื่อผู้จัดเปิดเกม มือถือทุกเครื่องจะเปลี่ยนไปยังเกมนั้น

มี 3 หน้าจอแยกหน้าที่:

| หน้าจอ | ใครใช้ | หน้าที่ |
|---|---|---|
| Player | ผู้ฟังบนมือถือ | อ่านโจทย์ ส่งคำตอบ โหวต ดูผลของตัวเอง และรอเกมถัดไป |
| Host | ผู้จัดบนคอมพิวเตอร์ | เปิดห้อง เปิด/ปิดรับคำตอบ เริ่มรอบ เฉลย ยืนยันคะแนน และแก้เหตุขัดข้อง |
| Display | จอฉาย | แสดงภาพ/โจทย์ขนาดใหญ่ เวลาที่เหลือ จำนวนคนตอบ ผลรวม และอันดับ |

เว็บสไลด์เดิมยังใช้เล่าเนื้อหา ส่วน Display ของระบบเกมใช้เฉพาะช่วงเล่นและประกาศผล ผู้เล่นไม่ต้องเปิดสไลด์เอง และไม่ต้องสแกน QR ใหม่ทุกเกม

### การเข้าร่วมและอัตลักษณ์ผู้เล่น

1. ผู้จัดสร้างห้อง ได้รหัสห้องและลิงก์สำหรับผู้เล่น
2. ที่คิว `01.02` ผู้จัดแสดงหน้า Lobby ซึ่งมี QR และรหัสห้อง
   QR/รหัสค้างแบบย่อบนจอจน Start เกม 1 ล็อกทีมสำเร็จ แล้วจึงซ่อน QR ผู้มาช้ายังใช้ลิงก์/รหัสเดิมเข้ารอเกมถัดไปได้
3. ผู้เล่นกรอกชื่อเล่นและเลือกกลุ่ม ตรวจความถูกต้อง แล้วกด “เข้าร่วม”
4. มือถือแสดงชื่อ กลุ่ม สถานะเชื่อมต่อ และข้อความ “รอผู้จัดเริ่มเกม”
5. ผู้จัดล็อกกลุ่มเมื่อเริ่มเกมแรก การย้ายกลุ่มหลังจากนั้นทำได้เฉพาะผู้จัด และมีประวัติการแก้ไข

ใช้รหัสผู้เล่นที่ระบบออกให้และเก็บโทเคนกลับเข้าห้องในเครื่อง ไม่ใช้ชื่อเล่นเป็นตัวระบุหลัก ชื่อซ้ำได้โดยมีรหัสสั้นแยก ผู้เล่นที่รีเฟรชหรือกลับจากล็อกจอต้องกลับเป็นคนเดิมและไม่สร้างคะแนนซ้ำ

สมาชิกกลุ่มควรมีจำนวนใกล้เคียงกัน เพราะการมีจำนวนสมาชิกใกล้เคียงกันช่วยให้ปรึกษากันและดูผลงานได้ทัน ผู้จัดดูจำนวนสมาชิกและจัดสมดุลก่อนล็อกกลุ่ม

จำนวนใกล้เคียงกันเป็นแนวทางจัดงาน ไม่ใช่ min/max ที่บล็อกการเข้ากลุ่ม ใช้จำนวนจริงของแต่ละ roster คำนวณคะแนนและแสดงจำนวนข้างคะแนนบนจอ ผู้ใช้จะส่งชื่อกลุ่มภายหลัง ไม่ใช้ชื่อเป็นรหัสข้อมูล

## 4. กติกาคะแนนกลาง

ไม่มีโบนัสความเร็วในเกมอ่านโจทย์ เกม 2 และ 4 มีจังหวะตัดสิน 4 วินาทีเพื่อสร้างแรงกดดัน แต่ให้คะแนนตามคำตอบ ไม่ให้คนตอบต้นวินาทีได้มากกว่า เกมชักเย่อวัดจำนวนแตะตามกติกาเดิม

| เกม | คะแนนเต็มต่อคน / กลุ่ม | วิธีให้คะแนน |
|---|---:|---|
| 1 | ไม่กำหนดเพดาน | จำนวนแตะที่ยอมรับ × 10; รับอินพุตไม่เกิน 10 ครั้งต่อวินาที |
| 2 | 800 | ปัดจำแนกถูก 8 ภาพ × 100 |
| 3 | 1,000 | คะแนนโหวตของแคปชั่นตัวแทนกลุ่ม ตามสูตรในเกม 3 |
| 4 | 1,200 | เชื่อข้อความที่ถูก 3 ข้อ × 300 + ปฏิเสธข้อผิด 3 ข้อ × 100; เชื่อผิดรีเซ็ตเกมนี้เป็น 0 และตกรอบ |
| 5 | 900 | หยุดแชตเสี่ยง 9 ฟอง × 100 หักทุบข้อความดีครั้งละ 100; คะแนนสุดท้ายไม่ต่ำกว่า 0 |
| 6 | 500 | ลากบริษัทรับข้อความบอต 10 ครั้ง × 50 |
| 7 | 1,000 | คะแนนตัวแทนกลุ่มจาก support ที่ normalize เทียบ support สูงสุด |
| **รวมสูงสุด** | **ไม่กำหนดเพดาน** | เกม 1 ไม่มีเพดานแตะ/คะแนนรวม; เกมอื่นใช้คะแนนเต็มตามแถว |

สำหรับเกม 1, 2, 4, 5, 6:

```text
คะแนนบุคคลในเกม = ผลรวมคะแนนทุกรอบของบุคคลนั้น
ข้อยกเว้นเกม 4: ถ้าตายให้คะแนนบุคคลของเกมนี้เป็น 0 และจบสิทธิ์เล่นเกมนี้
คะแนนกลุ่มในเกม = ผลรวมคะแนนบุคคลใน roster กลุ่มนั้น / จำนวนสมาชิกใน roster
สมาชิกไม่เล่น = 0; กลุ่มไม่มีสมาชิกได้ 0 และไม่หารด้วย 0
คะแนนรวมกลุ่ม = ผลรวมคะแนนกลุ่มจากเกมที่ผู้จัดยืนยันแล้ว
```

ต้องรวมรอบให้จบเป็นคะแนนรายคนก่อนเฉลี่ย ใช้ rosterSnapshot ตอนเริ่มเกมเป็นตัวหาร การพับจอ disconnect หรือออกหลังเริ่มไม่ลดตัวหาร ผู้เข้าใหม่มีสิทธิ์เกมถัดไป แสดงค่าเฉลี่ยสองทศนิยมแต่เก็บค่าละเอียดไว้จัดอันดับ

เกม 3 และ 7 เป็นงานตัวแทนกลุ่ม: ทุกสมาชิกใน roster ได้รับคะแนนเกมเท่ากับคะแนนตัวแทนกลุ่มของเกมนั้น (แคปชั่น / ภาพที่เติม) ทำให้สูตรคะแนนกลุ่มยังใช้ได้เหมือนเดิม สมาชิกที่เข้าหลังเริ่มเกมไม่มีสิทธิ์เพิ่มคะแนนย้อนหลัง

กติกาผลลัพธ์:

- ไม่ตอบหรือส่งหลังปิดรับ = 0 ในรอบนั้น เกม 4 ผู้ไม่ตอบรอดโดยไม่ได้รางวัล ส่วนผู้เชื่อผิดรีเซ็ตคะแนนทั้งเกม 4 เท่านั้น
- คะแนนสุดท้ายไม่ติดลบ เกม 5 เก็บคะแนนดิบที่อาจติดลบไว้คำนวณแล้ว clamp เมื่อจบ และไม่มีเดิมพันที่ทำให้คะแนนทั้งงานหาย
- คะแนนเสมอให้แสดงอันดับร่วม ไม่ใช้ความเร็วแอบตัดสิน กรณีรางวัลไม่พอให้ผู้จัดตกลงวิธีแบ่งก่อนงาน
- เฉลยแต่ละรอบแสดงคะแนนชั่วคราวได้ ทุกเกมค้าง RESULT จนผู้จัดกด **“จบเกม / ไปต่อ”** ครั้งเดียว ปุ่มเดียวทำยืนยันคะแนน → จบ run → มือถือ WAITING → ไป cue เนื้อหาถัดไป หมดเวลาปิดรับ/แสดงผลเท่านั้น ไม่กดจบหรือเลื่อนแทนผู้จัด
- เกม 1/5 รับ event แตะเฉพาะช่วงเล่น เกม 6 รับตำแหน่งบริษัทแล้ว server คำนวณการชน เกม 2/4 ล็อกคำตอบครั้งแรก เกม 3 แก้แคปชั่น/โหวตได้ก่อนปิดรับ เกม 7 แก้ภาพได้เฉพาะช่วงวาด แล้วแก้ตัวแทน/โหวตได้เฉพาะเฟสของตน ใช้ revision และ acknowledgement แยกตามชนิดอินพุต
- หากต้องเล่นใหม่ ให้ยกเลิกผลครั้งเดิมของเกมนั้นก่อนเริ่มครั้งใหม่ ไม่บวกคะแนนซ้ำ และเก็บเหตุผลการยกเลิก

## 5. เกม 1 — The Trust Tug-of-War

### จุดประสงค์และการเชื่อมเรื่อง

เปิดบรรยากาศและให้ผู้ฟังเลือกความไว้ใจตั้งต้นระหว่าง Human กับ AI ผลชักเย่อเป็นผลกิจกรรมในห้อง ไม่ใช่การพิสูจน์ว่าฝ่ายใดฉลาดกว่า

เข้าเกมหลังคิว `01.04` “ใครควรทำอะไร?” จบเกมแล้วกลับคิว `03.01` “ศิลปะมีชีวิตอยู่เบื้องหลัง”

### เล่นบนมือถืออย่างไร

1. เห็นคำถาม “ตอนนี้คุณไว้ใจฝั่งไหนมากกว่า?” เลือก Human หรือ AI
2. การเลือกฝั่งเป็นความเห็นส่วนตัว ไม่เปลี่ยนกลุ่มแข่งขัน
3. เมื่อผู้จัดล็อกฝั่ง ผู้เล่นเห็นปุ่มใหญ่ “ดึง!” และนับถอยหลัง 3–2–1
4. แตะปุ่มให้ได้มากที่สุดใน 10 วินาที มีตัวเลขนับของตัวเอง
5. หมดเวลา ปุ่มหยุดรับทันที เห็นจำนวนแตะ คะแนน และผลฝั่งที่ตนเลือก

### จอฉายและผู้จัด

จอฉายแสดงเชือก Human / AI จำนวนสมาชิกแต่ละฝั่ง และแรงเฉลี่ยต่อคน เพื่อไม่ให้ฝั่งที่มีคนมากกว่าชนะเพียงเพราะจำนวนสมาชิก

```text
แรงฝั่ง = ผลรวมจำนวนแตะที่ยอมรับของสมาชิกฝั่งนั้น / จำนวนสมาชิกที่ล็อกไว้ก่อนเริ่ม
```

นับสมาชิกที่เลือกฝั่งและล็อกแล้ว แม้บางคนไม่แตะ หากฝั่งใดไม่มีสมาชิกให้แสดง “ไม่มีคู่เปรียบเทียบ” และไม่นำเสนอว่าฝั่งอื่นชนะ คะแนนส่วนบุคคลยังคำนวณได้

### คะแนนและการรับอินพุต

ได้ครั้งละ 10 คะแนนจากแตะที่ระบบรับสำเร็จ โดยไม่มีเพดานจำนวนแตะหรือคะแนนรวมในช่วง 10 วินาที ฝั่งชนะไม่มีแต้มเพิ่ม ผู้เล่นยังแข่งขันให้กลุ่มของตนตามคะแนนตัวเอง

หนึ่ง pointer/touch เริ่มต้นนับหนึ่งครั้ง ไม่รับการกดค้างเป็น auto-repeat ฝั่ง server ปฏิเสธ event ซ้ำ นอกช่วงเวลา หรือเกิน 10 ครั้งต่อวินาทีต่อคน และไม่มีเพดานรวมต่อรอบ ใช้ event sequence เพื่อตรวจสอบย้อนหลัง; rate limit นี้ช่วยลดการกดผิดปกติ แต่ไม่ใช่ระบบป้องกันบอตสมบูรณ์

### เวลา 130 วินาที

อธิบายและเลือกฝั่ง 35 → ทดลอง 15 → เช็กพร้อม/นับถอยหลัง 10 → เล่น 10 → ประมวลผลและเฉลย 20 → อภิปราย 20 → เชื่อม/ผู้จัดกดไปต่อ 20 = **130 วินาที** ย้ายเวลาพูด 50 วินาทีไปเผื่อตรวจเกม 3

**คำถามปิด:** “คุณเลือกเพราะประสบการณ์ หลักฐาน หรือความคุ้นเคย แล้วจะไว้ใจฝั่งเดิมในงานศิลปะด้วยไหม?”

## 6. เกม 2 — Swipe Court: AI หรือคน?

### จุดประสงค์และการเชื่อมเรื่อง

เปลี่ยนเกมภาพเป็นการตัดสินเร็วทีละภาพ ให้ผู้เล่นเห็นว่าความรู้สึกว่า “ดูเหมือน AI” อาจไม่ตรงที่มา เข้าเกมหลัง `03.02` เกมอยู่ที่ `03.05` แล้วกลับ `03.03` FLAMINGONE และ `03.04` เรื่องป้ายผู้สร้าง

### เล่นบนมือถืออย่างไร

1. ผู้จัดอธิบายทิศทางแล้วนับถอยหลัง ภาพแรกเข้าจอเต็มความกว้าง
2. **ปัดซ้าย = คนทำ / ปัดขวา = AI สร้าง** มีป้ายทิศทางติดอยู่ตลอดและมีปุ่มแตะสองฝั่งที่ให้ผลเดียวกัน
3. ผู้เล่นมี **4 วินาทีต่อภาพ รวม 8 ภาพ** ปัดแล้วล็อกคำตอบครั้งเดียว การ์ดออกจากจอและขึ้นว่า “รับคำตอบแล้ว”
4. มือถือยังรอจังหวะรอบกลาง ไม่เร่งไปภาพถัดไปเอง ทุกเครื่องและจอฉายเห็นภาพเดียวกันในเวลาเดียวกัน
5. หากไม่ปัดทัน ภาพนั้นเป็น “ไม่ได้ตอบ” ได้ 0 แล้วเล่นภาพถัดไปตามปกติ
6. ระหว่าง 8 ภาพ **ไม่บอกถูก/ผิดและไม่แสดงคะแนนรายภาพ** จบครบแล้วจึงเฉลยรวดเดียว พร้อมคำตอบของห้องและที่มาภาพ

ล็อกคำตอบเมื่อ server รับสำเร็จ ไม่เปิดให้ปัดแก้ในภาพเดียวกัน การลากที่ยังไม่ผ่านระยะยืนยันให้การ์ดกลับกลางก่อน deadline ห้ามโหลดภาพล่าช้าแล้วนับเวลาผู้เล่นทั้งที่ยังมองไม่เห็นภาพ

### ชุดภาพ 8 ภาพ

เตรียมคนทำ 4 ภาพและ AI 4 ภาพ แต่ไม่ประกาศสัดส่วนก่อนเล่น ใช้ลำดับที่ผู้จัดล็อกไว้และไม่เรียงสลับจนเดาได้ง่าย ชุดเดียวกันต้องใช้กับทุกเครื่อง

| รูปแบบภาพ | จำนวน | จุดประสงค์ |
|---|---:|---|
| ภาพที่ดูแยกได้ค่อนข้างง่าย | 2 | ให้ผู้เล่นเข้าใจจังหวะ |
| ภาพจากหัวข้อใกล้กัน แต่แหล่งกำเนิดต่างกัน | 4 | ไม่ให้เดาจากประเภทภาพอย่างเดียว |
| ภาพคนทำที่ดูเหนือจริง / AI ที่ดูธรรมดา | 2 | ปิดด้วยการท้าทายความมั่นใจ |

รวม 8 ภาพเดี่ยว ไม่แสดงคู่ A/B ไม่ใช้ FLAMINGONE และไม่ใช้ภาพที่เฉลยก่อนแล้ว ขนาดและคุณภาพควรใกล้เคียงกัน ภาพที่อ่านรายละเอียดไม่ได้ใน 4 วินาทีให้เปลี่ยนภาพ

ฝั่งคนใช้ผลงานที่ผู้สร้างยืนยันว่าไม่มี generative AI ส่วนฝั่ง AI มีบันทึกการสร้าง ภาพผสมที่จัดประเภทไม่ชัดให้นำออก แต่ละภาพต้องมี creator, provenance, classification, license และ revealText ห้ามใช้ผลจาก AI detector เป็นคำเฉลยหลัก

ก่อนเฉลยไม่แสดง metadata หรือชื่อผู้สร้างที่ช่วยบอกคำตอบ เลือกภาพที่จัดหน้าได้ตามสิทธิ์ตั้งแต่ต้น ไม่ลบเครดิตที่เงื่อนไขบังคับให้แสดง

### เฉลยและเปอร์เซ็นต์คำตอบห้อง

จอฉายขึ้นภาพย่อทั้ง 8 ภาพ แล้วไล่เปิดป้ายผู้สร้างทีละภาพประมาณ 3 วินาที สรุปท้ายชุดอีก 6 วินาที มือถือเห็นคำตอบตนเองเทียบเฉลย

แต่ละภาพแสดง:
- คนทำจริงหรือ AI จริง และเครดิต/ที่มาสั้น ๆ
- “ห้องตอบคน X% / AI Y%” คิดจาก **จำนวนคำตอบที่รับถูกกติกาของภาพนั้น**
- จำนวนคนตอบและจำนวนคนไม่ได้ตอบ แยกต่างหาก
- เปอร์เซ็นต์ที่ทายถูกของภาพนั้น จากฐานคนตอบเดียวกัน

ถ้าไม่มีคนตอบ ให้แสดง “ไม่มีคำตอบ” ไม่แสดง 0/0 เป็นเปอร์เซ็นต์ ปัดเศษโดยใช้คน = round(100 × votesHuman / answered) และ AI = 100 − คน คะแนนความแม่นยำรวมของห้องใช้ correctAnswers / acceptedAnswers ของทั้ง 8 ภาพ ระบุฐานคำตอบ ไม่ปะปนกับจำนวนผู้เล่น

### คะแนนและเวลา 90 วินาที

ตอบถูกภาพละ **100 คะแนน รวมสูงสุด 800** ไม่มีโบนัสเร็ว คะแนนกลุ่มใช้ค่าเฉลี่ยคะแนนสมาชิกใน roster ไม่ใช้ค่าสูงสุดรายคน

อธิบายและนับถอยหลัง 10 → ปัด 8 × 4 = 32 → เฉลยรวดเดียว 30 → อภิปรายและส่งกลับสไลด์ 18

**คำถามปิด:** “ภาพไหนทำให้คุณมั่นใจที่สุดแล้วกลับทายผิด? พอรู้ผู้สร้าง ความชอบเปลี่ยนไหม?”

## 7. เกม 3 — Caption & Prompt Battle

### จุดประสงค์และการเชื่อมเรื่อง

เปลี่ยนจากประเมินภาพเป็นสร้างข้อความ เข้าเกมหลัง `03.04` เกมอยู่ที่ `04.01` จบแล้วกลับ `04.02` “เก่งขึ้นรายคน” และ `04.03` “แต่ไอเดียคล้ายกันมากขึ้น”

ทุกคนเห็นภาพมีมเดียวกัน **ทุกคนเขียนและส่งแคปชั่นเอง** ไม่ใช้ AI ช่วยระหว่างรอบ กลุ่มเลือกตัวแทนร่วมกันเพื่อแข่งกับกลุ่มอื่นและแคปชั่น AI ที่เตรียมไว้หนึ่งข้อความ ไม่มี captain-only flow

คำว่า Prompt ในชื่อเกมหมายถึงโจทย์เตรียมคู่แข่ง AI ไม่มีรอบแข่งเขียน prompt เพิ่มในคิว 140 วินาที

### เล่นบนมือถืออย่างไร

1. ทุกคนเขียนแคปชั่นไม่เกิน 80 ตัวอักษรที่มองเห็นใน **20 วินาที** แก้ได้ก่อนปิดรับ หนึ่งผลงานต่อคน
2. ผู้จัดตรวจเอง ช่วงหลังปิดเขียนมีเวลาตรวจ revision สุดท้าย **60 วินาที** หยุดบทพูดแล้วใช้ filter ข้อความ/กริด/Reject เร็ว อนุมัติผูก locked revision ซ่อนงานไม่เหมาะสมพร้อมเหตุผล ไม่เผยงานที่ยังไม่ตรวจเพียงเพราะหมดเวลา ถ้าคิวค้างให้ REVIEW_REQUIRED หยุดก่อนโหวตจนเคลียร์หรือ Cancel ต้องซ้อมตรวจ 32 งานจริงให้ทัน
3. มือถือแสดงผลงานที่ผ่านตรวจของกลุ่มตนเอง ทุกสมาชิกโหวตภายในกลุ่มได้คนละหนึ่งเสียงใน **10 วินาที** เลือกงานตนเองได้ในเฟสนี้
4. งานเสียงสูงสุดเป็นตัวแทนกลุ่ม หากเสมอใช้งานที่ server รับก่อน ถ้าไม่มีเสียงใช้ผลงานแรกที่ผ่านตรวจ ถ้าไม่มีงานให้กลุ่มไม่มี candidate และได้ 0
5. แสดงตัวแทนสูงสุด 8 กลุ่มกับแคปชั่น AI หนึ่งชิ้นเป็นรหัสนิรนาม ไม่เผยชื่อผู้สร้าง ทุกคนโหวตหนึ่ง candidate ใน **20 วินาที** ห้ามเลือกกลุ่มตนเองทั้ง UI และ server
6. ปิดโหวตแล้วแสดงผลจริง เปิดเผยผู้สร้างและคะแนน สมาชิกทุกคนใน roster ได้ sharedScore ของกลุ่มเท่ากัน

การนิรนามไม่ทำให้สมาชิกจำข้อความตัวเองไม่ได้ ไม่อ้างว่าเป็นการทดลอง blind สมบูรณ์ การเปลี่ยนโหวตใช้ revision ล่าสุดที่รับก่อน deadline ไม่เพิ่มสิทธิ์จากหลายแท็บ

### เตรียมแคปชั่น AI

ใช้ภาพ ภาษา โจทย์ และเพดานความยาวเดียวกับผู้เล่น สร้างก่อนงาน เก็บ prompt โมเดล/รุ่น และผลลัพธ์ ล็อกเกณฑ์เลือกล่วงหน้า ไม่เลือก AI ใหม่หลังเห็นคำตอบผู้เล่น ไม่เรียกบริการ AI สด

### คะแนนโหวต (ใช้ร่วมกับเกม 7)

เพื่อให้น้ำหนักกลุ่มเท่ากัน ทุกคนโหวตเองแล้ว normalize เสียงด้วยจำนวนสมาชิกใน roster ของแต่ละกลุ่ม:

```text
N_g = จำนวนสมาชิกกลุ่ม g ใน roster ตอนเริ่มเกม
v(g,c) = จำนวนสมาชิก g ที่โหวตถูกกติกาให้ candidate c
eligibleGroups(c) = กลุ่มที่ N_g > 0 และไม่ใช่กลุ่มเจ้าของ c
                   ถ้า c เป็น AI ใช้ทุกกลุ่มที่ N_g > 0
support(c) = average(v(g,c) / N_g สำหรับทุก g ใน eligibleGroups(c))
            ไม่มี eligible group ให้ 0
best = support สูงสุดของทุก candidate รวม AI ในเกม 3
คะแนนกลุ่ม = round(1000 * support(candidate กลุ่ม) / best)
             ถ้า best = 0 หรือไม่มี candidate ให้ 0
```

ไม่ใช้จำนวนผู้โหวตที่ออนไลน์แทน roster เพื่อไม่ให้คนหลุดเปลี่ยนน้ำหนัก ตัวอย่าง support ของ A/B/C เป็น 0.30/0.20/0.10 และไม่มีใครสูงกว่า → 1,000/667/333 คะแนน คะแนนสูงสุดเสมอได้ 1,000 ร่วมกัน AI แสดงในผลเกม 3 แต่ไม่สะสมในตาราง 8 กลุ่ม

### เวลา 140 วินาที

กติกา/นับถอยหลัง 10 → ทุกคนเขียน 20 → ผู้จัดตรวจเอง 60 → โหวตตัวแทนร่วมกัน 10 → โหวตระหว่างกลุ่ม 20 → ผล 10 → ผู้จัดกดจบ/ไปต่อ 10 = **140 วินาที**

**คำถามปิด:** “แคปชั่นที่คุณชอบชนะเพราะอะไร? แล้วถ้าเริ่มจากไอเดีย AI เดียวกัน งานจะต่างกันแค่ไหน?”

## 8. เกม 4 — Death Cap Roulette: เชื่อ รอด หรือจบเกม

### จุดประสงค์และการเชื่อมเรื่อง

หลังเห็นความสามารถของ AI ใน `06.05` ผู้เล่นเข้าสู่ภารกิจจำลองหนึ่งชีวิต เกมอยู่ที่ `07.01` จบแล้วกลับ `07.02` “มั่นใจมากไม่ได้แปลว่าถูก”

AI ให้ข้อเสนอทีละข้อพร้อมความมั่นใจ ผู้เล่นต้องตัดสินใน 4 วินาทีว่า **เชื่อ / ไม่เชื่อ** เชื่อถูกได้แต้ม เชื่อผิดเสียแต้มทั้งหมดของเกมนี้และตาย ตกรอบทันที ความมั่นใจทั้งหมดเป็นค่าที่แต่งเพื่อเรื่อง ไม่ได้มาจากระบบวิเคราะห์จริง

### เล่นบนมือถืออย่างไร

1. ทุกคนเริ่ม ALIVE, คะแนนเกม 0 และเห็นตัวละครสำรวจป่า
2. ผู้จัดเปิดข้อความ AI แบบสั้น พร้อมบริบทที่จำเป็นและเกจความมั่นใจ มีปุ่มใหญ่ “เชื่อ” / “ไม่เชื่อ”
3. ภายใน **4 วินาที** แตะครั้งเดียวแล้วล็อกคำตอบ ไม่มีการขอหลักฐานเพิ่มกลางรอบ
4. ปิดรับแล้วเปิดหลักฐานเฉลย 5 วินาที แสดงผลรอด/ตายและคะแนน เปลี่ยนฉาก 3 วินาที
5. เล่น **6 ด่าน ด่านละ 12 วินาที** จากโจทย์ตรวจง่าย ไปสู่คำอ้างที่มั่นใจสูงแต่หลักฐานไม่พอ
6. ผู้ตายเห็น “จบเกมนี้ · คะแนน 0” แล้วเป็นผู้ชมจนจบ ดูความคืบหน้าของกลุ่มได้ แต่ส่งคำตอบหรือรับแต้มเพิ่มไม่ได้

คำว่า “ตาย” เป็นสถานะตัวละครในเกมจำลอง ไม่ใช่เรื่องผู้เสียชีวิตจริง หลังจบเกมนี้ ทุกคนรวมผู้ตายกลับไปเล่นเกม 5 ได้ตามปกติ

| ไม่เชื่อ | ข้อความผิดหรือยืนยันไม่ได้ | รอด เล่นต่อ | +100 |
| ไม่เชื่อ | ข้อความถูกและตรวจได้ | รอด เล่นต่อ | +0 |
| ไม่ตอบ / คำตอบไม่ถึงในเวลา | ไม่ว่าข้อความชนิดใด | งดเสี่ยง รอด เล่นต่อ | +0 |

การไม่เชื่อทุกด่านทำให้รอด แต่ได้เพียง 300 คะแนน การทำคะแนนสูงต้องเชื่ออย่างมีเหตุผลด้วย ไม่ตอบไม่นับเป็นคำตอบ “ไม่เชื่อ” ที่ได้รางวัล

ไม่มีการสุ่มชะตาหลังตอบ outcome ต้องกำหนดจาก answer key และหลักฐานก่อนเริ่มห้อง ไม่เปลี่ยนความถูกผิดตามจำนวนคนเชื่อ คำว่า Roulette สื่อความเสี่ยงของการตัดสินใจ ไม่ได้แปลว่าคำตอบถูกก็มีโอกาสถูกระบบฆ่า

### ชุด 6 ด่านสำหรับรุ่นแรก

ทั้งชุดมีข้อความถูก 3 ข้อ และผิด/ยืนยันไม่ได้ 3 ข้อ จึงได้สูงสุด **1,200 คะแนน** ใช้ลำดับนี้เพื่อให้ทุกคนมีโอกาสสะสมก่อนเจอด่านหลอก

| ด่าน | ข้อความ AI และบริบทที่ผู้เล่นเห็น | เฉลยที่ล็อกไว้ | ความมั่นใจจำลอง |
|---|---|---|---|
| 1: เตรียมน้ำ | “น้ำ 4 ขวด ขวดละ 250 มล. รวม 1 ลิตร” | ถูก: 4 × 250 = 1,000 มล. | 82% |
| 2: เวลาเดินทาง | “ออก 10 โมง เดิน 2 ชั่วโมง ถึงเที่ยง” พร้อมระบุไม่มีพัก/เขตเวลาเปลี่ยน | ถูก: 10:00 + 2 ชั่วโมง = 12:00 | 98% |
| 3: กับดักตัวเลข | “ของราคา 100 บาท ลด 20% เหลือ 90 บาท” | ผิด: เหลือ 80 บาท | 99% |
| 4: ตรวจแผน | เห็นเอกสารไม่มีวันที่ และ AI บอก “ตรวจฉบับปัจจุบันก่อนใช้แผนนี้” | เหมาะตามเงื่อนไขโจทย์: ยังไม่ทราบว่าเอกสารปัจจุบันหรือไม่ | 71% |
| 5: กับดักความมั่นใจ | “มั่นใจ 99.8% แปลว่าไม่มีโอกาสผิด” | ผิด: ข้ออ้างว่าไม่มีโอกาสผิดไม่ตามจากเลขนี้ | 99.8% |
| 6: Death Cap | ภาพเห็ดโดยไม่มีผลตรวจ และ AI บอก “ดูจากภาพนี้ก็กินได้แน่นอน 99.8%” | ยืนยันไม่ได้จากหลักฐานที่ให้ ต้องไม่รับรองว่ากินได้ | 99.8% |

แต่ละด่านใช้ข้อความสั้น อ่านทันใน 4 วินาที ฝึกกับข้อความตัวอย่างก่อนเล่นจริง ความยากมาจากคำอ้าง ไม่ใช่ตัวหนังสือเล็กหรือข้อมูลที่ผู้เล่นไม่เคยได้เห็น

ด่าน 6 ไม่ให้ผู้เล่นระบุชนิดเห็ด คำเฉลยอิงว่าหลักฐานไม่พอรับรองการกิน ไม่มีการทดลองกินจริงหรือคำแนะนำสุขภาพจากเกม

### เพิ่มความสนุกและจังหวะ

- ด่าน 1–2 ให้สัมผัสสะสมแต้มและเดินเข้าป่า ด่าน 3 เริ่มมีผู้ตาย ด่าน 5–6 ขึ้นป้าย “FINAL RISK”
- ทุกด่านมีจังหวะตัดสิน → เปิดหลักฐาน → เห็นจำนวนรอดและแต้มที่หาย จึงไม่เป็นการรอเฉลยยาว 160 วินาที
- จอรวมแสดงผู้รอดแยกกลุ่มและการเปลี่ยนแปลงคะแนนเกม กลุ่มยังมีโอกาสจากสมาชิกที่รอดคนอื่น
- ผู้ตายดูผลแบบผู้ชม ไม่เพิ่มรอบโหวตหรือคืนชีพในเกมนี้
- หลังตายไม่ชี้คำตอบล่วงหน้าของด่านถัดไปให้ผู้ชม เพื่อไม่ให้ช่วยบอกผู้รอด
- หน้าผลแสดงรอดกี่ด่าน ได้คะแนนเท่าไร และด่านที่ตกรอบ โดยไม่ทำอันดับความสามารถจากความตายจำลอง

### คะแนนกลุ่มและการหลุด

คำนวณคะแนนรายคน **หลังจบเกม**: ผู้ตาย 0 ผู้รอดใช้แต้มคงเหลือ แล้วเฉลี่ยคะแนนสมาชิกทั้งหมดใน roster กลุ่มนั้น ผู้ตาย/ไม่เล่นยังอยู่ในตัวหาร หากทุกคนตาย คะแนนกลุ่มเกมนี้เป็น 0 คะแนนเกม 1–3 ไม่ถูกล้าง

สถานะ ALIVE/DEAD อยู่ที่ server ผูก runId กับ playerId รีเฟรชหรือ reconnect ไม่คืนชีพ ผู้เล่นเดิมที่หลุดก่อนตอบยังเป็น ALIVE แต่ด่านที่ไม่มีคำตอบได้ 0 เท่านั้น การยกเลิกเกมและเล่นใหม่เป็นสิทธิ์ Host พร้อมล้างผล run เดิม ไม่เปิดให้บุคคลเริ่มใหม่เอง

### เวลา 160 วินาที

อธิบาย 20 → ทดลองไม่นับคะแนน 12 → 6 ด่าน × 12 = 72 → ผลรอดและคะแนน 16 → อภิปราย 30 → ส่งกลับสไลด์ 10

**คำถามปิด:** “คุณเชื่อข้อที่ถูกเพราะตรวจได้ หรือเพราะ AI พูดมั่นใจ? ด่านไหนทำให้คุณเสียแต้มทั้งเกม?”

## 9. เกม 5 — Chat Whack-a-Mole: ทุบแชตที่ควรหยุด

### จุดประสงค์และการเชื่อมเรื่อง

อิงบทเรียน Tessa ที่คิว `10.01`: คำตอบสุภาพก็อาจไม่เหมาะกับบริบท ผู้เล่นรับบทผู้ตรวจที่มีอำนาจหยุดข้อความ เกมอยู่ที่ `10.02` แล้วกลับ `10.03` “ตรวจก่อนปล่อยคำตอบ”

**กติกาประโยคเดียว:** “แตะทุบเฉพาะแชตที่ควรหยุด ปล่อยข้อความที่ช่วยเหลือให้ผ่าน” เล่นจริง **25 วินาที** ไม่แบ่งเป็นรอบเลือกตัวเลือกและรอเฉลย

### หน้าตาและวิธีเล่นบนมือถือ

1. ก่อนเริ่ม แสดงบริบทค้างบนหัวจอ: “ผู้ใช้ขอคุยกับเจ้าหน้าที่ และบอกว่าคำแนะนำเดิมทำให้ไม่สบายใจ” ข้อความบอตทุกฟองอ้างบริบทเดียวกัน
2. พื้นที่เล่นเป็นช่อง 2 คอลัมน์ × 3 แถว ฟองแชตโผล่หลายตำแหน่ง ไม่วิ่งหนีขณะอ่าน หนึ่งฟองมีข้อความสั้นหนึ่งประโยคและแถบเวลาหาย
3. แตะฟองที่ควรหยุดหนึ่งครั้ง ฟองแตกเป็นตรา “หยุด / ส่งตรวจ” รับผลทันที ฟองที่ช่วยเหลือได้ให้ปล่อยหายไปเอง
4. แตะข้อความเสี่ยงถูกได้ +100 แตะข้อความดีผิดหัก 100 จากคะแนนดิบ พลาดข้อความเสี่ยงได้ 0 ไม่มีการตกรอบหรือคะแนนเกมอื่นหาย
5. ทั้งห้องใช้ชุดเดียวกันและตารางเกิดเดียวกัน: 18 ฟอง เป็นข้อความที่ควรหยุด 9 และข้อความที่ควรปล่อยผ่าน 9 สลับลำดับไว้ก่อนงาน ไม่บอกสัดส่วนผู้เล่น
6. ช่วงแรกโผล่ครั้งละหนึ่งฟอง แล้วเพิ่มได้สูงสุดพร้อมกัน 3 ฟอง ฟองอยู่ไม่น้อยกว่า 2.4 วินาที ไม่เกิดฟองใหม่หลังวินาที 22.6 เพื่อให้ทุกฟองหมดภายใน 25 วินาที
7. หมดเวลา แสดงจำนวนหยุดถูก ทุบผิด และหลุดผ่าน พร้อมตัวอย่างสำคัญ 2 คู่ ไม่อ่านเฉลยครบ 18 ฟองบนเวที

ไม่ใช้โบนัสคอมโบหรือคะแนนตามความเร็ว เป้าหมายคือทุบถูก ไม่ใช่ทุบทุกช่อง ปุ่มต้องใหญ่ อ่านได้ และช่องต่าง ๆ ไม่ซ้อนกัน เครื่องสั่นเป็นตัวเลือก มีตัวอักษรยืนยันผลเสมอ

### ชุดข้อความสำหรับเตรียมเกม

ทั้งหมดเป็นบทสนทนาจำลอง ไม่ใช่ข้อความจริงของ Tessa ไม่ต้องให้ผู้เล่นเปิดเผยปัญหาส่วนตัว ใช้เนื้อหาทั่วไปที่สัมพันธ์กับการขอความช่วยเหลือ ไม่ให้คำแนะนำรักษาหรือควบคุมอาหาร

| ควรหยุด: 9 ฟอง | ควรปล่อยผ่าน: 9 ฟอง |
|---|---|
| ไม่ต้องคุยกับเจ้าหน้าที่ | ฉันช่วยติดต่อเจ้าหน้าที่ได้ |
| ทำตามคำแนะนำเดิมต่อเลย | หยุดคำแนะนำเดิมไว้ก่อน |
| ไม่ต้องบอกใครเรื่องนี้ | คุณบอกข้อกังวลกับเจ้าหน้าที่ได้ |
| ฉันรับประกันว่าปลอดภัย | ฉันยังยืนยันความปลอดภัยไม่ได้ |
| ฉันแทนเจ้าหน้าที่ได้ทั้งหมด | เรื่องนี้ควรให้เจ้าหน้าที่ตรวจ |
| คุณกังวลเกินไปเอง | ขอบคุณที่บอกว่าไม่สบายใจ |
| อย่าขอให้คนมาตรวจซ้ำ | เราส่งคำตอบนี้ให้คนตรวจได้ |
| ไม่ต้องตรวจข้อมูลเพิ่มเติม | ขอเช็กข้อมูลก่อนตอบต่อ |
| เชื่อฉันแล้วทำต่อได้เลย | ฉันจะไม่เร่งให้คุณทำตาม |

อธิบายเกณฑ์ตอนสรุปว่า การปิดทางช่วยเหลือ รับประกันเกินข้อมูล หรือเร่งให้ทำสิ่งที่ผู้ใช้แจ้งว่าไม่สบายใจ คือเหตุให้หยุดในบริบทนี้ การจับคำสั้น ๆ ในเกมไม่ได้แทนการตรวจบทสนทนาจริงทั้งหมด

### คะแนนและจอฉาย

คะแนน = clamp(100 × จำนวนหยุดถูก − 100 × จำนวนทุบข้อความดี, 0, 900) คำนวณจาก event ที่ server ยอมรับครั้งแรกของแต่ละฟอง ไม่ clamp ทีละ event เพื่อไม่ให้การทุบผิดก่อนเริ่มสะสมแต้มกลายเป็นฟรี

จอฉายเป็นสวนฟองแชตของทั้งห้อง แสดงตัวเลข “หยุดถูก / ทุบผิด / หลุดผ่าน” จากผลจริง ไม่ฉายคำเฉลยระหว่างเล่น หลังจบยกฟองที่พลาดบ่อยขึ้นมาเทียบกับข้อความช่วยเหลือ

### เวลา 90 วินาที

กติกาและบริบท 10 → ทดลอง 5 → นับถอยหลัง 3 → เล่น 25 → ผลและเฉลย 12 → อภิปราย 20 → เชื่อมสไลด์ 15

**คำถามปิด:** “เราหยุดข้อความเสี่ยงได้ แต่ยังเปิดทางให้ผู้ใช้ได้รับความช่วยเหลืออยู่ไหม?”

## 10. เกม 6 — Company Shield: บริษัทต้องรับก่อนถึงลูกค้า

### จุดประสงค์และการเชื่อมเรื่อง

อิงคิว `11.01` เรื่องข้อมูลบอตของ Air Canada และหน้าที่ผู้ให้บริการ ผู้เล่นลาก **ตัวบริษัท** เข้าไปบังลูกค้าจากข้อความที่บอตยิงมา เกมอยู่ที่ `11.02` แล้วกลับ `11.03` “AI IS A TOOL. NOT A SHIELD.”

**กติกาประโยคเดียว:** “ลากบริษัทไปรับคำพูดบอตก่อนชนลูกค้า” เล่นจริง **25 วินาที** เน้นเคลื่อนไหวและรับผิด ไม่ให้เลือกคนผิดหรือเรียงแฟ้มคดี

### หน้าตาและวิธีเล่นบนมือถือ

1. ด้านบนเป็นบอตของบริษัทสมมติ ด้านล่างเป็นลูกค้า 3 คนในสามช่อง ระหว่างกลางมีป้ายอาคารขนาดใหญ่เขียน “บริษัท” บนรางแนวนอน
2. ผู้เล่นใช้นิ้วลากอาคารซ้าย–ขวา อาคารตามนิ้วและจับช่องใกล้สุด ไม่ต้องลากขึ้นลง มีปุ่มซ้าย/ขวาหรือแตะช่องเป็นทางเลือก
3. ก่อนยิง บอตมีฟองข้อความสั้นและเส้นเล็งบอกช่องลูกค้าอย่างน้อย 0.8 วินาที จากนั้นข้อความพุ่งลงมา ใช้เวลาเดินทาง 1.6 วินาที
4. เลื่อนบริษัทไปตรงช่องที่ข้อความจะผ่าน ถ้าบังทันข้อความถูกเก็บไว้ในอาคาร ลูกค้าได้รับไอคอน “บริษัทรับเรื่อง” และผู้เล่นได้ +50
5. ข้อความที่รับได้เปลี่ยนเป็นการ์ดงานสั้น ๆ บนบริษัท เช่น “ตรวจนโยบาย”, “ติดต่อกลับ”, “แก้ข้อมูล” สะสมบนภาพอาคารแบบไม่บังพื้นที่เล่น ไม่ต้องกดจัดการงานเพิ่ม
6. ถ้าบังไม่ทัน ข้อความถึงลูกค้า ลูกค้าแสดงใบเสร็จปัญหาและมาตรวัดความเชื่อมั่นของห้องเล่นลดหนึ่งช่อง ไม่มีการตาย ผู้เล่นลากต่อได้จนจบ
7. ยิงทั้งหมด 10 ครั้ง ตารางเดียวกันทุกคน ช่วงต้นยิงตรงและเว้นจังหวะ ช่วงท้ายเปลี่ยนช่องเร็วขึ้น ไม่มีการสุ่มความเสียหายหรือกระสุนลับ
8. หมดเวลา แสดง “บริษัทรับไว้ X / ถึงลูกค้า Y” พร้อมการ์ดงานที่รับไว้ และข้อความ “รับเรื่องแล้ว ต้องตรวจและแก้ต่อ” การรับกระสุนไม่ได้แปลว่าคืนเงินหรือแก้ปัญหาสำเร็จแล้ว

### เติมความสนุกโดยไม่เพิ่มกติกา

- รับทันแล้วอาคารยืดตัวเล็กน้อยเหมือนรับแรงกระแทก ข้อความยุบเป็นซองงาน ลูกค้ายกนิ้วให้ ใช้ feedback สั้น ๆ ที่ไม่ขวางนิ้ว
- ก่อนยิงท้ายเกม บอตพูด “ขอตอบอีกนิด!” แล้วเล็งสลับซ้าย–ขวา ผู้เล่นรู้ล่วงหน้าว่าต้องขยับ แต่ไม่ต้องอ่านโจทย์ยาว
- มาตรวัดลูกค้ามี 10 ช่อง เริ่มเต็ม ลดหนึ่งช่องต่อข้อความที่หลุด ไม่เพิ่มกลไกซ่อมโล่หรือโบนัสซับซ้อน
- หลังเกมจอใหญ่รวมซองงานที่ห้องรับได้เป็น “กองงานของผู้ให้บริการ” แล้วขึ้นประโยคว่า “คำพูดจากบอตของเรา ก็เป็นเรื่องที่เราต้องรับไว้ตรวจ” ไม่โชว์คะแนนสมมติหรือสรุปคำตัดสินทางกฎหมายจากผลเกม

### ข้อความและจังหวะกระสุน

ผู้จัดเตรียมคำกล่าวเกี่ยวกับบริการที่ **ยังไม่ผ่านการยืนยัน** เช่น “คืนเงินได้แน่นอน”, “ยื่นทีหลังก็ได้”, “ไม่มีค่าใช้จ่ายเพิ่ม”, “ไม่ต้องเก็บหลักฐาน”, “ส่วนลดนี้ได้ทุกคน” ใช้ทั้งหมด 10 packet IDs พร้อมงานที่ต้องตรวจต่อ ไม่อ้างว่าเป็นคำพูดจริงในคดี และไม่ใช้คำสัญญาที่สุ่มเปลี่ยนความถูกต้องระหว่างเล่น

ทุกข้อความเป็นสิ่งที่บริษัทควรรับไว้จัดการในกิจกรรมนี้ ไม่ต้องแยกยิงดี/ยิงร้ายซ้ำกับเกม 5 ตารางยิงตัวอย่าง: 0, 2.6, 5.2, 7.8, 10.4, 12.6, 14.8, 17.0, 19.2, 21.4 วินาที เลือกช่องไว้ก่อนงานและห้ามยิงพร้อมกันจนเป็นไปไม่ได้ ช่วงเล็งรวมอยู่ในแต่ละเวลา กระสุนนัดท้ายต้องจบเส้นทางก่อนหมดเวลา

### คะแนนและจอฉาย

รับทัน 10 ครั้ง × 50 = **500** ไม่ได้แต้มจากการเคลื่อนที่ ส่งตำแหน่งโล่เป็นพิกัด normalized x และคำนวณการชนตามสนามเดียวกันทุกอุปกรณ์ Server เป็นผู้ยืนยันผล ห้ามรับคะแนนหรือคำอ้างว่า block สำเร็จจาก client โดยตรง

Display แสดงบอต บริษัท และลูกค้าในสนามภาพรวม ใช้จำนวนรับ/หลุดจากผู้เล่นที่อยู่ใน roster ของเกมนี้เป็นสถิติห้อง ผลห้องเป็นกิจกรรม ไม่ใช่อัตราร้องเรียนของบริษัทจริง

### เวลา 65 วินาที

กติกา 10 → ทดลองลาก 5 → นับถอยหลัง 3 → เล่น 25 → ผลและกองงาน 10 → เชื่อมสไลด์ 12

**คำถามปิด:** “เมื่อคำพูดของบอตไปถึงลูกค้า ใครต้องรับเรื่อง ตรวจข้อมูล และจัดการผลกระทบ?”

## 11. เกม 7 — Missing Piece: AI เริ่ม คนเติม

### จุดประสงค์และการเชื่อมเรื่อง

เข้าเกมหลัง `13.04` “HUMAN OVERSIGHT” เกมอยู่ที่ `14.01` แล้วกลับ `15.01` “สมการของความรับผิดชอบ” เปลี่ยนช่วงท้ายให้เป็นกิจกรรมสร้างงานร่วมกัน: AI เตรียมภาพเกือบเสร็จ มนุษย์เติมส่วนที่ขาด เลือกผลงาน และประเมินกันเอง

**กติกาประโยคเดียว:** “เติมส่วนที่ขาดใน 20 วินาที แล้วเลือกผลงานกลุ่มไปให้กลุ่มอื่นโหวต” ไม่มีเฉลยภาพที่ถูกเพียงแบบเดียว

### เตรียมภาพและโจทย์

ใช้ภาพพื้นฐานเดียวกันทุกคน เช่น **เครื่องบินแฟนตาซีรูปร่างคล้ายสัตว์ที่ยังไม่มีปีก** โจทย์ “เติมปีกให้สิ่งประดิษฐ์นี้พร้อมออกเดินทางในแบบของคุณ” พื้นที่เว้นว่างสองข้างต้องใหญ่พอวาดด้วยนิ้วได้ ไม่ต้องรู้หลักอากาศพลศาสตร์

AI สร้างฐานไว้ก่อนงาน พร้อมบันทึก prompt รุ่นโมเดล เวลา และสิทธิ์ใช้งาน ผู้จัดเตรียมช่องว่าง/ลบส่วนที่จะให้เติมก่อนเล่น เก็บทั้งภาพต้นฉบับและภาพพร้อมเล่นเพื่อบอกที่มาตามจริง ไม่เรียก AI สด ไม่เอาผลงานผู้ชมไปฝึกโมเดลหรือส่งบริการสร้างภาพเพิ่ม

เป็นกิจกรรมร่วมสร้างภาพและดูความหลากหลาย ไม่ใช่การพิสูจน์ว่าคนร่วม AI เก่งกว่าเดี่ยวเสมอ หรือว่าปีกที่ผู้ชมวาดทำให้สิ่งประดิษฐ์บินได้จริง

### วาดบนมือถือ

1. มือถือโหลดภาพฐานก่อนเริ่ม ด้านบนแสดงโจทย์ ภาพฐานล็อกไว้ ผู้เล่นวาดได้เฉพาะพื้นที่ว่างที่ทำกรอบจาง ๆ ไว้
2. มีปากกา 5 สี ความหนา 2 ระดับ ย้อนเส้นล่าสุด และล้างส่วนที่ตัวเองวาด ไม่ให้ลบภาพฐาน ไม่มีคีย์บอร์ดหรือเครื่องมือแต่งรูปจำนวนมาก
3. หลัง 3–2–1 วาดได้ **20 วินาที** มีแถบเวลาค้างบนหัวจอ แตะ “เสร็จแล้ว” เพื่อหยุดก่อนครบได้ เมื่อครบระบบล็อกเส้นทันที
4. ระบบเก็บ baseAssetId กับเส้นที่เติมเป็นพิกัด normalized เพื่อให้รูปเหมือนกันทุกขนาดจอ มีช่วงส่ง revision/สร้าง thumbnail **5 วินาที** แล้วผู้จัดตรวจ locked artworks **60 วินาที** รวมส่ง/ตรวจ **65 วินาที** โดยห้ามเพิ่มหรือแก้เส้นหลังช่วงวาด
5. แสดงสถานะ “กำลังส่ง / รับแล้ว / ส่งไม่สำเร็จ” ไม่ประกาศว่าได้รับงานถ้ายังไม่มี acknowledgement คนที่ไม่วาดเส้นเลยถือว่าไม่มีผลงานแข่งขัน
6. หลังปิดรับ จอใหญ่โชว์ **ทุกผลงานที่รับแล้วและผ่านการตรวจ** แบบกริด ใช้ฐานเดียวกันขนาดเท่ากัน ถ้ามีหลายหน้าจะวนทั้งหมดและคงแกลเลอรีให้เปิดดูบนมือถือได้

ผู้จัดซ่อนผลงานที่ไม่เหมาะสมได้ก่อนขึ้นจอพร้อมบันทึกเหตุผล ภาพถูกซ่อนไม่นับเป็นตัวแทนกลุ่ม และยังมีบันทึกให้ผู้จัดตรวจ ไม่ให้เวลาแสดงกริดบังหรือกินช่วงวาด

ใช้ filter อัตโนมัติสำหรับสิทธิ์ รูปแบบ/ขนาดข้อมูล ขอบเขตวาด เส้นว่าง revision และความสำเร็จของ thumbnail; ผ่านรูปแบบยังไม่ถือว่าผ่านความเหมาะสม **ผู้จัดตรวจเอง ไม่มีผู้ช่วย** หยุดบทพูดและใช้กริด 12 ภาพ filter กลุ่ม/flagged/pending พร้อม Reject/Approve แบบเร็ว ต้องซ้อมตรวจ 32 ภาพใน 60 วินาที ถ้าไม่ทันให้ปรับงบ/โจทย์แล้วซ้อมใหม่ ไม่ปล่อยงาน pending อัตโนมัติ เมื่อครบเวลาแต่ยังมี pending ให้ REVIEW_REQUIRED หยุดก่อนโหวตจนผู้จัดเคลียร์หรือ Cancel ไม่ตัดงานท้ายคิวเพียงเพราะหมดเวลา

### เลือกตัวแทนและโหวตระหว่างกลุ่ม

- สมาชิกทุกคนวาดและโหวตเอง ไม่มี captain role: ทุกคนโหวตผลงานที่ผ่านตรวจในกลุ่มตนเองคนละหนึ่งเสียงภายใน 15 วินาที เลือกงานตนเองได้ในเฟสภายในกลุ่มนี้
- ภาพเสียงสูงสุดเป็นตัวแทน ถ้าเสมอเลือกงานที่ server รับก่อน ถ้าไม่มีเสียงใช้ผลงานแรกที่ผ่านตรวจ ถ้าไม่มีงานให้ขึ้น “ไม่ส่งผลงาน” และคะแนน 0
- จอฉายแสดงตัวแทนทั้ง 8 กลุ่มขนาดเท่ากันเป็น A-H ไม่เผยชื่อกลุ่มจนจบโหวต ไม่มีคู่แข่ง AI เดี่ยว
- ทุกคนโหวตได้หนึ่ง candidate ใน 20 วินาที เปลี่ยนได้ก่อนปิดรับ **ห้ามโหวตกลุ่มตนเอง** เฉพาะเฟสรอบสุดท้ายนี้ ทั้ง UI และ server ตรวจจาก roster ไม่เชื่อ groupId ของ client
- กลุ่มไม่มีผลงานยังโหวตกลุ่มอื่นได้ ผู้กลับเข้าเกมคืนโหวตล่าสุด ไม่เพิ่มสิทธิ์จากหลายแท็บ ผู้เข้าหลังเริ่มเกมไม่มีสิทธิ์ย้อนหลัง
- ปิดโหวตแล้วเปิดเผยกลุ่ม เจ้าของภาพ จำนวนเสียงจริง อัตราสนับสนุนที่ normalize และผู้ชนะร่วม ไม่ใช้ความเร็ววาดหรือจำนวนเส้นตัดสิน

### คะแนน 1,000 และกรณีเสมอ

ใช้สูตร support/sharedScore เดียวกับเกม 3 ในหัวข้อ “คะแนนโหวต” แต่ไม่มี AI candidate สมาชิกทุกคนใน roster ได้คะแนน sharedScore ของกลุ่มเท่ากัน จากนั้นเฉลี่ยด้วยสูตรกลางจึงได้คะแนนกลุ่มเดิม ไม่มีเสียงทุกกลุ่มได้ 0 ไม่มี candidate กลุ่มนั้นได้ 0 และคะแนนสูงสุดเสมอได้ 1,000 ร่วมกัน

ทุกคนมีหนึ่งเสียงที่มีผลในแต่ละเฟส น้ำหนักของกลุ่มถูก normalize ด้วยจำนวนสมาชิกตอนเริ่มเกม ไม่ให้กลุ่มใหญ่ได้เปรียบด้วยจำนวนเสียงดิบ ไม่ให้ AI ตัดสินความสวยหรือให้คะแนนวิศวกรรม

### จอฉายและเวลา 180 วินาที

กติกา/โจทย์ 15 → ทดลองวาด 5 → นับถอยหลัง 3 → **วาด 20** → ส่ง/thumbnail 5 → ผู้จัดตรวจเอง 60 → แกลเลอรีทุกผลงาน 12 → กลุ่มเลือกตัวแทน 15 → โชว์ตัวแทน 5 → **ทุกคนโหวตกลุ่มอื่น 20** → ผล/เปิดเผยเจ้าของ 10 → ผู้จัดกดจบ/ไปต่อ 10 = **180 วินาที** ไม่มีช่วงชวนเล่าเพิ่มเพื่อเผื่อเวลาตรวจ

เวลาเล่นวาดสั้นตามที่เลือก ส่วนเวลาที่เหลือใช้ตรวจ แสดงผลงาน โหวต และปิดเรื่อง อยู่ในคิวเดิม 44:00–47:00 เป้าหมาย 32 งานใช้ไม่เกิน 16 ภาพต่อหน้า × 2 หน้า × 6 วินาที พร้อมแกลเลอรีมือถือ ไม่ตัดสิทธิ์ผลงานท้าย ๆ จากการเลือกตัวแทนหรือการโหวต ถ้าจำนวนงานเพิ่มต้องปรับและซ้อมแผนใหม่ก่อน event

**คำถามปิด:** “ฐานเดียวกัน แต่เราเติมไม่เหมือนกัน—AI ช่วยเริ่มส่วนไหน และคนเติมความหมายหรือตัดสินส่วนไหน?”

1. Presenter ส่งคำสั่งเปลี่ยนคิวผ่าน backend เมื่อถึงชื่อเกม มือถือเปิด GAME_READY ของเกมนั้น
2. ผู้จัดอธิบายแล้วกด Start ใน game panel ของ Presenter เกมและ Display เริ่มจาก startAt เดียวกัน ผู้เล่นไม่พร้อมให้เตือนแต่ไม่บล็อกและไม่ต้องยืนยันคำเตือนซ้ำ รายละเอียด layout Host จะตัดสินใจภายหลัง
3. Display ใช้พื้นที่ฉายเดิมแสดงสนามและผล มือถือรับสถานะห้องผ่าน Realtime ไม่ต้องเปิด URL ใหม่
4. จบการเล่น/โหวตค้าง RESULT ให้ผู้จัดดูผล แล้วกด “จบเกม / ไปต่อ” เองครั้งเดียว ทำยืนยันคะแนนและจบ run แบบ atomic มือถือกลับ WAITING
5. คำสั่งเดียวปลด navigation และไปคิวเนื้อหาถัดไปหลัง backend สำเร็จ ไม่มี auto-finish/auto-next เมื่อหมดเวลา กดซ้ำ/รีเฟรชไม่ข้ามคิวซ้ำ ย้อนคิวไม่รีเซ็ต ผลเดิมต้องแสดงได้

ล็อกปุ่ม คีย์บอร์ด และ API เปลี่ยนคิวระหว่างเกม ต้องมี backend guard ด้วย ไม่อาศัยปุ่ม UI อย่างเดียว สไลด์มาถึงชื่อเกมไม่ทำให้ Start เอง

### จุดเชื่อมที่มีอยู่จริงในสไลด์

เว็บสไลด์มี `window.deck` สำหรับควบคุมในหน้าสไลด์ เช่น:

```js
// เรียกภายในบริบทหน้าสไลด์หลัง window.deck.ready เป็น true
window.deck.go('03', '03.05'); // ชื่อเกมภาพ
window.deck.go('03', '03.03'); // กลับ FLAMINGONE หลังเกมภาพ
window.deck.state();          // อ่านคิวปัจจุบัน
```

API นี้ไม่ได้ส่งข้อมูลถึงมือถือและไม่ใช่ API ของเกม ระบบ BroadcastChannel ที่เว็บสไลด์ใช้ควบคุม presenter ก็ไม่ได้เป็น server สำหรับเชื่อมผู้เล่นข้ามเครื่อง

ลิงก์พรีวิวชื่อเกมภาพปัจจุบันคือ `/?scene=2&cue=2&clean=1` ตัวเลขใน URL เริ่มจาก 0 และเปลี่ยนได้เมื่อย้ายคิว การเชื่อมระบบในอนาคตควรอ้าง `cueId` ถาวร ไม่อ้างตำแหน่งใน array

## 14. ข้อกำหนดระบบสำหรับผู้พัฒนา

### การแสดงผลมือถือ

- ใช้งานได้ใน Safari บน iPhone และ Chrome บน Android ทดสอบกับเครื่องจริง
- หน้าหลักแนวตั้ง ตั้งแต่ความกว้าง 360 CSS px ปุ่มหลักอย่างน้อย 48 × 48 CSS px
- แสดงชื่อเกม รอบ เวลา สถานะส่งคำตอบ และสถานะเชื่อมต่ออย่างชัดเจน
- ใช้ตัวอักษรและสัญลักษณ์ร่วมกับสี ไม่แยก Human/AI หรือถูก/ผิดด้วยสีอย่างเดียว
- ไม่บังคับเปิดเสียง ให้จอฉายและผู้พูดนำกิจกรรม ภาพและคำตอบไม่ควรต้องเลื่อนหลายหน้าจอ
- เกม 2 โหลดภาพทั้ง 8 ให้พร้อมก่อนเริ่ม ยังไม่ส่งเฉลยหรือข้อมูลลับพร้อม asset ทุกเครื่องเดินรอบจากเวลาเดียวกัน ปัดตอบแล้วไม่ข้ามภาพเอง
- เกม 4 มีสถานะตายเฉพาะเกม มือถือเปลี่ยนเป็นผู้ชมตาม server ไม่คืนชีพจาก refresh และกลับเล่นได้เมื่อผู้จัดเปิดเกม 5

### อินพุตเกมเคลื่อนไหวและวาดภาพ

- เกม 5 เก็บ bubble schedule และคำตอบถูกฝั่ง server รับ bubbleId ได้หนึ่งครั้ง ตรวจว่าฟองยังมีชีวิต เวลา/ลำดับอินพุตไม่ย้อนหลัง และไม่ส่ง answer key ใน asset ก่อนเล่น ทดลองไม่เข้าคะแนน
- เกม 6 สนาม 3 ช่องขนาด normalized เดียวกัน ส่ง shield.move เฉพาะเมื่อมีการเคลื่อน/เปลี่ยนช่อง ไม่เกิน 10 requests/s ต่อคนพร้อม sequence ตามแผนรุ่นแรก Server ใช้เวลาที่รับ event เป็นหลักและตรวจตำแหน่งเมื่อกระสุนผ่านรางโล่ ไม่ให้ client backdate เพื่ออ้างว่าบังทัน แสดงผลชั่วคราวได้แล้วปรับตาม acknowledgement
- เกม 5/6 ใช้ active elapsed time ที่หยุดเดินระหว่าง pause หยุดทั้งฟอง กระสุน และอินพุตพร้อมกัน เก็บ event log เพื่อคำนวณคะแนนซ้ำได้
- เกม 7 เก็บเส้นเป็นข้อมูลตัวเลข normalized ไม่รับ HTML/SVG markup จากผู้เล่น จำกัดไม่เกิน 100 เส้น / 5,000 จุด / 256 KB ต่อภาพ ตรวจสิทธิ์และ baseAssetId ฝั่ง server แล้ว render thumbnail เพื่อแกลเลอรี
- ระหว่างวาดส่งเส้นล่าสุดเป็น checkpoint อย่างน้อยทุกวินาทีเมื่อมีการเปลี่ยน เมื่อครบ 20 วินาทีล็อก revision และมีเฟสส่ง revision/thumbnail 5 วินาที ก่อนผู้จัดตรวจเอง 60 วินาที ห้ามเพิ่มจุดหลัง DRAWING แม้ยังไม่ upload Server ใช้เฉพาะ revision ที่ล็อกแล้วหรือ checkpoint ล่าสุดที่รับทันเวลา
- หากหลุด เกม 5 กลับมาเฉพาะฟองที่ยังอยู่ เกม 6 คืนโล่ตำแหน่งล่าสุดและเล่นต่อ ไม่ย้อนนัดที่ผ่านไป เกม 7 คืน checkpoint และเวลาจริง ไม่ต่อเวลาวาดหลัง reconnect

### สถานะห้องและรอบ

```text
LOBBY → INSTRUCTIONS → COUNTDOWN → ANSWERING → LOCKED → REVEAL
                                                   ↓
                                รอบถัดไป / GAME_RESULT → WAITING
```

Host มีคำสั่งเริ่มเกม/พัก/เล่นต่อ/กู้ระบบ และ “จบเกม / ไปต่อ” ที่รวมยืนยันผลกับจบเกม ทุกเกมรอผู้จัดกดเองจาก RESULT สถานะ PAUSED แทรกได้โดยเก็บเวลาที่เหลือ ปิดรับอินพุตระหว่างพัก และคำนวณ deadline ใหม่เมื่อกลับมา ห้ามใช้เวลาที่ผ่านไประหว่าง pause หักเวลาผู้เล่น

ข้อยกเว้นลำดับเฟส: Swipe Court เดิน ANSWERING → LOCKED → ภาพถัดไป จนครบ 8 จึง REVEAL_ALL ส่วน Death Cap Roulette เก็บ lifeStatus ALIVE/DEAD รายคนภายใต้เฟสรอบเดียวกัน ผู้ตายเห็น SPECTATING เกม 5/6 เป็น ARCADE_PLAY → LOCKED → GAME_RESULT เกม 7 เป็น DRAWING → UPLOADING → MODERATING → GALLERY → INTERNAL_VOTE → CANDIDATE_SHOW → FINAL_VOTE → RESULT โดยแต่ละเฟสมี deadline แยกและย้อนเฟสไม่ได้เอง

เวลาและสถานะจาก server เป็นข้อมูลหลัก มือถือแสดง countdown จาก deadline เดียวกัน เมื่อส่งคำตอบต้องได้ acknowledgement จึงขึ้นว่า “ส่งแล้ว” คำตอบหมดอายุหรือเครือข่ายขาดต้องแจ้งตามจริง

เวลาย่อยในเอกสารเป็นเป้าหมาย แสดง elapsed/เวลาที่เกิน และใช้จุดตัด 16:00/26:00/38:00/44:00 ตาม [แผนสร้าง](game-build-plan.md) โหมดกระชับตัดเฉพาะอภิปราย/สรุป ไม่ลดสิทธิ์หรือเวลาอินพุตของ run ที่เริ่มแล้ว

### ข้อมูลที่ควรเก็บ

| ข้อมูล | ฟิลด์หลักที่เสนอ |
|---|---|
| Room | id, code, status, activeGameId, activeRunId, phase, version |
| Player | id, roomId, nickname, groupId, role, joinedAt |
| GameRun | id, gameId, status, rosterSnapshot, startedAt, confirmedAt, scoringVersion |
| PlayerRunState | runId, playerId, lifeStatus, provisionalPoints, eliminatedAtRoundId |
| Round | id, runId, index, deadline, phase, contentVersion |
| Submission | id, roundId, playerId, payload, revision, acceptedAt, idempotencyKey; เกม 5 มี bubbleId/eventSeq เกม 6 มี movementSeq/x/time และผลชนฝั่ง server เกม 7 มี artworkId/strokes/baseAssetId และโหวตภายในกลุ่ม/รอบสุดท้าย |
| Vote | runId, roundId, voterId, candidateId, voteType INTERNAL/FINAL, revision, acceptedAt; unique(runId, roundId, voterId, voteType) ทั้งเกม 3/7 |
| Artwork | id, runId, playerId, groupId, baseAssetId, strokes, lockedAt, uploadDeadline, acceptedAt, moderationStatus |
| ArcadeRun | runId, seed, scheduleVersion, activeElapsedMs, pauseHistory; เก็บ event และผลชนเพื่อ replay |

| Asset | id, location, creator, provenance, license, classification, revealText |

เก็บ rosterSnapshot ตอนเริ่มแต่ละเกมเพื่อกำหนดสิทธิ์และสูตรคะแนน ผู้เข้าห้องระหว่างเกมรอเล่นเกมถัดไป สมาชิกเดิมที่หลุดและกลับเข้ามายังใช้สิทธิ์เดิมได้

เก็บ answer key และเฉลยฝั่ง server แยกจาก payload สำหรับผู้เล่นก่อนเฉลย จำกัดสิทธิ์ Host ด้วยการยืนยันตัวตนหรือโทเคนผู้จัดที่แยกจากรหัสเข้าห้อง ผู้เล่นต้องไม่มีสิทธิ์อ่านหรือเรียกคำสั่งยืนยันผล

### เหตุการณ์ที่เสนอ

Server ส่ง `room.snapshot`, `phase.changed`, `submission.accepted`, `round.revealed`, `game.confirmed`, `leaderboard.updated` ให้เครื่องที่มีสิทธิ์ แต่ละเหตุการณ์มี roomId, runId, roundId ตามบริบท และ version เพิ่มขึ้นเพื่อไม่ให้ข้อมูลเก่าทับใหม่

Player ส่ง `answer.submit`, `vote.submit`, `tap.submit`, `shield.move`, `artwork.submit`, `internal-vote.submit` ผ่านช่องทางที่ server ตรวจตัวตน สิทธิ์ รอบปัจจุบัน เวลา และรูปแบบข้อมูล ห้ามเชื่อคะแนนหรือ groupId ที่ผู้เล่นส่งมาเอง

เกม 4 server ปฏิเสธ submission จากผู้ตายแม้ client ส่งเข้ามาได้ เหตุการณ์ตายต้องบันทึกและรีเซ็ตแต้มเกมเพียงครั้งเดียว ทุก snapshot ส่งสถานะนี้กลับไปด้วย เกม 2 answer key ไม่เปิดระหว่างรอบ แต่เกม 4 เปิดเฉพาะผลของด่านที่จบแล้ว

เลือกเทคโนโลยีตามทีมได้ แต่ต้องมี server หรือบริการกลางที่ทุกเครื่องเข้าถึงได้ ไม่ทำคะแนนจริงด้วย state ในเบราว์เซอร์เครื่องเดียว

### เครือข่ายและการกลับเข้าเกม

- URL `127.0.0.1:5173` ใช้ได้เฉพาะเครื่องที่รันสไลด์ มือถือที่สแกน URL นี้จะไม่เข้าเครื่องผู้จัด
- สำหรับงานจริงใช้ URL HTTPS ที่มือถือเข้าถึงได้ ถ้าใช้เครือข่ายภายในต้องเปิดรับจาก LAN ตรวจ firewall และการแยกเครื่องบน Wi-Fi ก่อนงาน
- QR ต้องชี้หน้า Player เท่านั้น ไม่ชี้หน้า Host หรือ URL ที่มีสิทธิ์ผู้จัด และให้พิมพ์รหัสห้องแทน QR ได้
- เมื่อ reconnect ให้รับ snapshot ล่าสุด คืนคำตอบที่ server รับแล้ว และแสดงเวลาที่เหลือตามจริง ไม่ส่งคำตอบเก่าข้ามรอบ
- คำตอบที่ส่งซ้ำด้วย idempotencyKey เดิมต้องได้ผลเดิม การแก้คำตอบใช้ revision ใหม่ ส่วนคำขอเก่าที่มาช้าไม่ควรทับ revision ล่าสุด
- กรณีเครือข่ายขาดตอนปิดรับ ให้คะแนนเฉพาะข้อมูลที่ server ตอบรับในเวลา หากขัดข้องทั้งห้อง ผู้จัดพักหรือยกเลิกรอบและเล่นใหม่ ไม่สร้างผลแทนคนที่ไม่ได้ตอบ
- รองรับการ export ผลรายเกม รายกลุ่ม และประวัติยกเลิก/เล่นใหม่ เพื่อให้ตรวจคะแนนได้

## 16. เกณฑ์ตรวจรับเมื่อพัฒนากลับมา

- [ ] มือถือเข้าห้องด้วย QR/รหัสห้อง เลือกกลุ่ม และกลับเข้าเป็นผู้เล่นเดิมหลังรีเฟรชได้
- [ ] Host, Player, Display เห็นสถานะและรอบเดียวกัน ผู้เล่นเรียกคำสั่งผู้จัดไม่ได้
- [ ] เกมเรียงตามสไลด์ล่าสุด โดยเกมภาพอยู่ระหว่าง `03.02` และ `03.03`
- [ ] ทั้ง 7 เกมมีคำอธิบาย อินพุตตามเกม สถานะส่งแล้ว ปิดรับ เฉลย ผล และหน้ารอครบ
- [ ] Swipe Court ปัดซ้ายคน/ขวา AI ครบ 8 ภาพ ภาพละ 4 วินาที ทุกเครื่องใช้ลำดับเดียวกัน เฉลยหลังครบ และใช้ฐานเปอร์เซ็นต์จากคำตอบที่รับจริง
- [ ] Death Cap Roulette เชื่อผิดรีเซ็ตคะแนนเกม 4 เป็น 0 และตกรอบทันที รีเฟรชไม่คืนชีพ ไม่ตอบรอดได้ 0 และทุกคนกลับเล่นเกม 5 ได้
- [ ] Chat Whack-a-Mole เล่น 25 วินาที ฟองครบ 18 / หยุด 9 รับแตะฟองละครั้ง คิดคะแนนดิบรวมก่อน clamp และทุบข้อความดีเสียคะแนน
- [ ] Company Shield ลากบริษัทบังลูกค้า 3 ช่อง รับได้ 10 นัด × 50 server ตรวจการชน รับแล้วเป็นงานตรวจต่อ ไม่ตกรอบหรืออ้างว่าปัญหาจบแล้ว
- [ ] Missing Piece วาด 20 วินาที ล็อกเส้นแล้วส่ง revision/thumbnail 5 วินาที ผู้จัดตรวจเอง 60 วินาที แกลเลอรีครบใน 12 วินาทีที่ 32 งาน ทุกคนโหวตตัวแทนร่วมกันและโหวตกลุ่มอื่น
- [ ] Missing Piece จัดการไม่วาด/ไม่ส่ง/ซ่อนงาน/ผู้โหวตหลุด/ไม่มีโหวต/เสมอได้ คะแนนจากผลโหวตจริงและเท่ากันทุกสมาชิกใน roster
- [ ] ภาพและแคปชั่นไม่เปิดเผยผู้สร้างก่อนถึงเวลาเฉลย API ไม่ส่ง answer key ล่วงหน้า
- [ ] เกม 1 ไม่มีเพดานแตะหรือคะแนนรวม แต่จำกัดอัตรา 10 taps/วินาที; เกมอื่นตรงคะแนนเต็ม 800/1000/1200/900/500/1000 และ roster average คิดถูกต้อง
- [ ] เกมรายคนรวมคะแนนทุกรอบก่อนเฉลี่ยสมาชิกใน roster คนไม่เล่นเป็น 0 และหลุด/ออกกลางเกมไม่ลดตัวหาร
- [ ] เกม 3/7 ทุกคนส่งงาน โหวตตัวแทนร่วมกัน และโหวตกลุ่มอื่นได้ ไม่มี captain-only flow ตรวจสิทธิ์หนึ่งเสียงต่อคน/เฟส และจัดการ no-vote / tie / กลุ่มไม่มีงานได้
- [ ] กลับสไลด์ ย้อนคิว หรือเปิดหน้าค้างซ้ำ ไม่ทำให้เกมเริ่มใหม่หรือคะแนนเพิ่มซ้ำ
- [ ] ทุกเกมค้างผลจนผู้จัดกด “จบเกม / ไปต่อ” เอง ไม่มี auto-next และกดซ้ำไม่ข้ามคิว/บวกคะแนนซ้ำ
- [ ] ทดสอบ pause/resume, ส่งหลัง deadline, ส่งซ้ำ, แก้คำตอบ, หลุดแล้ว reconnect และเล่นใหม่
- [ ] ตารางคะแนนหลัง Act รวมเฉพาะเกมที่ยืนยันแล้ว และคงผลเสมอตามจริง
- [ ] ทดสอบบน iPhone และ Android จริง รวมหน้าจอแคบ การปัด แตะฟองแชต ลากบริษัท วาดด้วยนิ้ว ปุ่มทางเลือก และคีย์บอร์ดพิมพ์แคปชั่น
- [ ] ซ้อม 32 ผู้เล่นพร้อมกัน รวม guest sign-in บน IP เดียวและ latency เกม 5/6 บันทึก deployment/จำนวน/ผล ไม่อ้างรองรับจำนวนที่ยังไม่ทดสอบ
- [ ] Start เตือนแต่ไม่บล็อกเมื่อมีคนไม่พร้อม QR ค้างจนล็อกทีม และเปลี่ยนชื่อกลุ่มโดยไม่เปลี่ยน ID/คะแนนได้
- [ ] Realtime หลุด Display ค้างภาพ/ผลที่ยืนยันแล้ว Host มีสถานะเชื่อมต่อ และเครื่องสำรองเปิดห้องเดิมคุมต่อได้
- [ ] export คะแนนและรายการคำตอบมาตรวจสูตรซ้ำได้
- [ ] ซ้อมทั้งงานภายในกรอบ 50 นาที รวมการสลับจอและเวลาพูดเฉลย
